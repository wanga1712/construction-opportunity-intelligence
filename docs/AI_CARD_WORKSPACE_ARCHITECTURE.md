# AI Card Workspace / Card Context Architecture

> **Статус:** архитектурная спецификация развиваемого контура. Реализация
> ведётся отдельно от текущего production pipeline.

## 1. Основная концепция

ИИ-ассистент работает не как абстрактный чат по закупкам вообще, а как
**интеллектуальное рабочее место (AI Workspace), развёрнутое вокруг конкретной
карточки объекта/закупки**.

При открытии карточки закупки или объекта пользователь взаимодействует с
моделью, имеющей доступ ко всему собранному досье:

```text
OPPORTUNITY / OBJECT
│
├── Structured Card Data (CRM, заказчик, цены, дедлайны, этапы)
│
├── Procurement Metadata (ЕИС, протоколы, разъяснения, требования)
│
├── Documents (архивы, файлы, проектная и рабочая документация)
│   ├── Notice (извещение)
│   ├── Technical Assignment (ТЗ)
│   ├── Project Documentation (ПД)
│   ├── Working Documentation (РД)
│   ├── Estimates (ЛСР, ВОР, сметные расчеты)
│   └── Contract Draft (проект договора)
│
├── Knowledge Base (нормативная база, ГОСТ, СП, технические регламенты)
│
├── Evidence & Findings (подтвержденные факты, совпадения, контекст, цитаты)
│
├── Research Provenance (история исследований, цепочка источников, валидация)
│
└── Card Chat Session State (история диалога по карточке, рабочие гипотезы)
```

## 2. Компоненты контекста карточки

Контекст карточки собирается по принципу многоуровневого индекса:

1. **Card Summary & Core Metadata**: номер закупки, статус, закон
   (44-ФЗ / 223-ФЗ), заказчик, НМЦК, дедлайн, регион.
2. **Factual Evidence Layer**: извлеченные и валидированные `V4 CONFIRMED`
   кандидаты материалов и оборудования.
3. **Document Inventory & Parse Cache**: реестр физических файлов и архивов с
   метаданными.
4. **Relevant Document Chunks (RAG / Lexical Search)**: семантические и
   полнотекстовые фрагменты проектной документации и ТЗ.
5. **Regulatory & Technical Norms**: ссылки на применимые СП, ГОСТ и
   технические условия.
6. **Provenance Timeline**: временная шкала событий по карточке.

## 3. Примеры сценариев диалога

1. *«Что здесь вообще требуется сделать?»* — структурированная выжимка
   предмета работ и состава объекта.
2. *«Какие материалы и оборудование мы можем поставить?»* — поиск целевых
   номенклатур (гидроизоляция, напольные покрытия, светотехника, трубные
   системы).
3. *«Какие объемы и площади гидроизоляции заложены в сметах?»* — извлечение
   физических объемов из локальных сметных расчетов.
4. *«Есть ли требования к членству в СРО или лицензиям?»* — анализ требований
   к участникам закупки.
5. *«Какие ключевые риски и штрафные санкции в проекте контракта?»* —
   правовой анализ договора.
6. *«Можно ли согласовать замену проектного материала на аналог?»* — проверка
   требований ТЗ на эквивалентность и ГОСТ.
7. *«Составь план коммерческой проработки этого объекта.»* — пошаговый
   чек-лист для менеджера.

## 4. Разделение ответственности

```text
LLM WEIGHTS (Языковая модель: рассуждения, синтез, извлечение)
    ↓
KNOWLEDGE LAYER (Нормативная база, стандарты, СП, ГОСТ)
    ↓
OPERATIONAL DATA (CRM, объекты, закупки, участники, сметы)
    ↓
CONTEXT BUILDER (Формирование активного контекста turn-by-turn)
    ↓
AI CARD SESSION (Интерактивная сессия пользователя)
```

Нормативные требования, операционные данные CRM и веса модели не смешиваются
в единую сущность.

## 5. Оптимизация и кэширование

Для эффективной работы с крупными пакетами строительной документации
архитектура предусматривает:

- `PROMPT_CACHE` / `PREFIX_CACHE` — кэширование неизменяемого системного
  промпта и базового досье карточки на уровне инференс-провайдера;
- `KV_CACHE` — переиспользование состояния внимания между последовательными
  вопросами пользователя в рамках одной карточки;
- `DOCUMENT_CHUNK_CACHE` — предварительно подготовленные эмбеддинги и чанки
  документов;
- `CONTEXT_PACK_CACHE` — кэширование скомпонованных пакетов контекста для
  частых сценариев.

## 6. Границы полномочий и безопасность

На первом этапе AI Workspace функционирует исключительно в режиме чтения:
`READ_ONLY = YES`.

**ИИ разрешено:**

- читать и анализировать документацию;
- выполнять поиск по архивам и сметам;
- формировать выжимки, таблицы и сравнения;
- давать пояснения и цитировать первоисточники.

**ИИ запрещено без явного подтверждения пользователя:**

- менять статус закупки или этап CRM;
- изменять очередь обработки документов;
- выполнять мутации в базе данных;
- отправлять внешние запросы или подавать заявки;
- изменять утвержденную экспертную разметку.

## 7. Единая идентичность объекта

Карточка объекта (`Opportunity / Object`) представляет собой единую
неразрывную сущность:

```text
                        ЕДИНЫЙ ОБЪЕКТ
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
 Аналитический           CRM закупок             CRM систем
    контур             (генподрядчики,          гидроизоляции
(макро-аналитика)         поставки)           и спецматериалов
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              │
                     FULL CARD KNOWLEDGE
                              │
                        AI WORKSPACE
```

## 8. Связанный Analytics V2 command center

Верх страницы «Аналитический контур V2» — плотный операционный экран,
который собирается из одного read-only снимка
(`src/services/analytics_command_center.py`, `load_analytics_command_snapshot()`)
и кэшируется на 60 секунд. Ни один блок не делает собственный запрос в БД.

| Блок | Что показывает | Источник |
| :--- | :--- | :--- |
| LIVE-строка | свежесть хранилищ и сервисов | system health snapshot |
| Активные торги | открытый приём заявок, разбивка 44-ФЗ / 223-ФЗ | `crm_procurements` + actionable rule |
| Pipeline | узлы контура и потери между ними | CRM + document queue |
| Матрица категорий | закупка × товарная категория | `crm_procurement_category_opportunities` |
| Medal transition | `candidate_initial_medal` → `current_effective_medal` | category opportunities |
| Документы | статусы и причины ошибок | `document_intelligence` |
| Состояние серверов | health-блок | `src/ui/system_health_page.py` |

Правила экрана:

- «Идут торги» означает реально открытый приём заявок, а не
  `crm_stage='torgi'`;
- единица медальных метрик — category opportunity, а не закупка;
- ошибка отдельного запроса отображается как «Нет данных», но не как ноль;
- raw exception и pipeline-диагностика находятся в collapsed техническом
  expander;
- возврат на вкладку не повторяет тяжёлые SQL-запросы.

Строка категории выводится только при наличии хотя бы одной opportunity.
Активные категории без возможностей не превращаются в нулевые KPI.
