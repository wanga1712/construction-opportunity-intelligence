# Контур поиска по документам: DIRECT vs PROJECT (дизайн)

Статус: **проектное решение, к реализации по этапам.** Ничего не удаляем и не
перезаписываем: старые находки остаются историей.

## 1. Проблема (зафиксировано на реальных данных)

- Матчер грузит **всю таксономию** — `keywords_loaded: total=596` — и гоняет её
  по каждому документу каждой закупки, **без привязки к категории**.
- Итог: в «Поставке вычислительного сервера» находятся `путепровод`,
  `осушение`, `пропитка`, `250×1000` (термины дорожных/композитных категорий),
  плюс generic-стемы `управлен`, `операцион`, `административ` со 100 баллами
  (`FUZZY_TOKEN_SET` = `partial_ratio`, стем — подстрока слова).
- Стоимость: сложность `ключи × строки` на файл; при 596 ключах и ТЗ на
  2–5 тыс. строк это ~1–3 млн fuzzy-вызовов на файл, ×10–70 файлов на задачу.
  Релевантных для закупки терминов — десятки, т.е. переплата ~10–50×.

## 2. Как должно быть

### 2.1. Прямая поставка (DIRECT_GOODS / DIRECT_SUPPLY)

**Мы уже знаем, что поставляют** (категорию присвоила модель/правила), поэтому
keyword-поиск по таксономии для прямых закупок **не нужен вообще** — ни свой,
ни чужой. Задача другая: **разобрать саму поставку**.

Извлекаем по документу:

- **полная смета / спецификация** — из чего состоит закупка (позиции, кол-во,
  ед. изм., цена за ед., сумма) → **нормализация через ИИ** (названия позиций,
  единицы, сопоставление с реестром);
- **технические параметры** закупаемого (характеристики, бренд/модель, ГОСТ/ТУ);
- **требования к поставщику** (лицензии, опыт, соответствие);
- **требования к поставке** (сроки, адрес/базис, условия приёмки, гарантия);
- **условия участия** (обеспечение, порядок, ограничения).

То есть для DIRECT основной источник данных — **смета + требования**, а не
совпадения терминов. Keyword-слой для DIRECT не создаёт находок; при
необходимости он используется только для уточнения подкатегории.

### 2.2. Объект / в составе работ (EMBEDDED_MATERIAL, PROJECT)

Пока без изменения логики, **кроме одного**: не искать всё подряд.

- Категории для закупки уже определены (модель потратила ресурс заранее —
  «путь от обратного»), поэтому в документах ищем **только термины этих
  категорий**.
- Термины без `category_codes` — только строгий `EXACT`, роль `CONTEXT`,
  находок не создают.

### 2.3. Роли терминов (общее для обоих)

`ENTITY` (сам товар/материал) · `QUALIFIER` (уточнение, напр. «класс 34/43») ·
`CONTEXT` (объект/работы) · `NOISE` (общие слова, стемы-обрубки).
Находку формирует только `ENTITY`; всё остальное — атрибут или отбрасывается.
Кросс-категорийный guard: термина чужой категории не может подтвердить закупку.

## 3. Этапы

1. **Scope по категории — только для PROJECT/EMBEDDED** (самый дешёвый и самый
   большой эффект там): матчер получает только ключи категорий закупки
   (`keyword_meta[k].category_codes` ∩ категории opportunities) → 596 → десятки.
   Код scope уже задеплоен (`MatchEngine.for_categories`, `daemon._scoped_engine`).
2. **Роли и guard (PROJECT)**: `ENTITY/QUALIFIER/CONTEXT/NOISE`,
   кросс-категорийное вето, ограничение усечения стемов.
3. **DIRECT-экстрактор (главный для прямых поставок)**: смета/спецификация →
   **нормализация через ИИ**, техпараметры, требования к поставщику, требования к
   поставке, условия участия. Keyword-поиск здесь не используется.
   Блокер данных: у категории `computers` в таксономии **0** search-терминов —
   для PROJECT-scope это значит «нет ключей»; для DIRECT это неважно, т.к. идём
   по смете.
4. **UI**: для DIRECT — вкладки «Смета», «Техпараметры», «Требования»;
   для PROJECT — «Категорийные находки» (как сейчас), всё в карточке закупки.

## 4. Ограничения

- Scoring, пороги медалей, lifecycle и историю не меняем.
- Старые находки не удаляем; новые правила применяются к новым прогонам,
  старые остаются `LEGACY_UNVERIFIED` и отсекаются фильтром.
- XML-парсеры S7 не трогаем.

## 5. Новое правило: материальные позиции ≥ 200 000 ₽ в сметах объектов/проектов

### 6.0. Согласование с параллельной разработкой шаблонов парсинга

В проекте уже есть слой «поисковых тем со скорингом» — **не создаём второй**:

- `crm_product_groups`, `crm_search_profiles`, `crm_search_rules` (`value` +
  `weight`) — это шаблоны/профили поиска: что искать и с каким весом
  (см. `docs/MULTI_PROFILE_SEARCH_RULES.md`, `docs/DB_PROFILED_SEARCH_SCHEMA.sql`);
- `document_match_details` (+ provenance) — найденные **доказательства**.

Правила для DIRECT-экстрактора с учётом этой параллельной работы:

1. Экстрактор **не вводит собственный скоринг и веса** — он поставляет
   структурированные сущности (позиция сметы, техпараметр, требование) с
   привязкой к документу/строке, то есть в формате **evidence**.
2. Тема/вес берутся из существующих `crm_search_rules` / `search_profiles`;
   если для позиции сметы правила ещё нет — она становится кандидатом (как в §5),
   а не новой параллельной записью со своим весом.
3. ИИ-нормализация формирует **search-темы** (`value`) для профиля, после чего
   скоринг идёт штатным механизмом (weight), а результаты — в
   `document_match_details` как доказательства.
4. Никаких изменений в самих `crm_search_rules` без отдельного согласования:
   сначала пишем кандидатов, показываем в карточке, и только затем — запись.

Закупка «Поставка вычислительного сервера» (№ 32616445095), 3 документа:

Вывод: контур DIRECT — это **извлечение таблиц спецификации + техпараметров +

### 6.1. Где именно лежат требования (проверено 2026-10-10)

Требования к участнику/поставке — это в основном **текстовые абзацы**, а не
таблицы, поэтому табличный экстрактор их не видит. Реальное расположение:

| Документ | Блок | Где |
|---|---|---|
| `Приложение №1.docx` (ТЗ) | «Общие требования», «Товар должен соответствовать требованиям Технических регламентов, ГОСТ, ТУ…», «Весь товар должен быть новым… Поставка восстановленного товара не допускается», гарантия/техподдержка ≥ 3 года | абзацы |
| `Документация.docx` | **требования к участнику и условия участия**: термины «Участник закупки — …», «Заявка на участие…», «Преференция…», ссылка на ПП РФ № 1875 (нацрежим), обеспечение исполнения договора | абзацы (112 попаданий по ключам) |
| `Документация.docx` | таблица `Код ОКПД2 \| Вид требования по национальному режиму` → `26.20.14.120 \| Ограничение` | таблица |
| `Приложение №2 _Проект Договора_.docx` | условия исполнения: обеспечение, изменение объёма ≤ 30 %, запреты/ограничения | абзацы |

Следствие для экстрактора DIRECT: нужны **два слоя** — табличный (спека,
техпараметры, нацрежим) и **текстовый с секциями**: «Требования к участнику»,
«Требования к товару/поставке», «Условия участия», «Обеспечение»,
«Национальный режим». Границы секций определяются по заголовкам/ключевым
абзацам, тело секции — следующие абзацы до следующего заголовка.

### 5.1. Смысл

Для объектов и проектов коммерческая возможность не ограничивается заранее
присвоенными категориями: в смете могут стоять **материалы и оборудование на
поставку**, которые в текущий реестр категорий не попали. Их надо не «искать
всем словарём», а **вычислять по сумме**: строки поставки материалов с суммой
**≥ 200 000 ₽**.

Таким образом для PROJECT/EMBEDDED:

- keyword-поиск — только по категориям закупки (см. §2.2), чужие не ищем;
- дополнительно — **правило порога**: из смет выделяются строки поставки
  материалов с суммой ≥ 200 000 ₽ (порог конфигурируемый).

### 5.2. Что делаем со строками

1. Каждая такая строка сохраняется **отдельно** как кандидат (не смешивается с
   категорийными находками и не считается подтверждённой категорией).
2. Повторяемость: если одна и та же позиция/материал встречается **несколько
   раз** (в строках/в разных похожих проектах) — записывается как
   **кандидат-категория** (по правилу «несколько раз встретилось → категория»).
3. Накопление идёт по похожим проектам; когда срабатывает триггер (набралось N
   повторов по кандидату) — кандидат уходит **в модель**: нормализация названия,
   генерация поисковых фраз/слов для новой категории.
4. После успешной нормализации — запись в БД через **существующий реестр
   категорий** (не свободные строки), после чего категория становится обычной и
   далее работает общий контур (admission, scoring, медали — без изменения
   правил).

### 5.3. Набросок контракта данных (к согласованию перед реализацией)

```
material_supply_candidates          -- новая таблица-кандидат (только новый контур)
  id, procurement_id, detail_id, source_document, page/row,
  raw_text, product_name_raw, quantity, unit, unit_price, total_price,
  threshold_passed (total_price >= 200000), occurrence_key, occurrence_count,
  status: NEW | ACCUMULATING | SENT_TO_MODEL | ACCEPTED_CATEGORY | REJECTED,
  first_seen_at, last_seen_at, model_run_id, created_category_code
```

- `occurrence_key` — нормализованный ключ позиции (для подсчёта повторов).
- Триггер: `occurrence_count >= N` (N конфигурируемый, по умолчанию к
  согласованию) → `SENT_TO_MODEL`.
- Запись категории — только через реестр (`crm_product_categories` /
  `crm_product_subcategories`), с автором/источником `AUTO_CANDIDATE`.

### 5.4. Ограничения

- Порог 200 000 ₽ — **конфигурируемый**, а не «магическое» число в коде.
- Scoring, пороги медалей и lifecycle не меняются; новые категории не получают
  медаль автоматически (`UNSCORED`, пока не оценены штатным контуром).
- Никакой автозаписи в реестр без модели и без триггера; история не
  перезаписывается.
- Реализация — отдельным этапом после §3.1 (scope по категории) и §3.2 (роли).
