# Контур поиска по документам: DIRECT vs PROJECT (дизайн)

Статус: **проектное решение, к реализации по этапам.** Ничего не удаляем и не
перезаписываем: старые находки остаются историей.

## 1. Проблема (зафиксировано на реальных данных)

- Матчер грузит **всю таксономию** — `keywords_loaded: total=596` — и гоняет её
  по каждому документу каждой закупки, **без привязки к категории**.
- Итог: в «Поставке вычислительного сервера» находятся `путепровод`,
  `осушение`, `пропитка`, `250×1000` (термины дорожных/композитных категорий),
  плюс generic-стемы `управлен`, `операцион`, `административ` со 100 баллами
  (`FUZZY_TOKEN_SET` = `partial_ratio`, стем — подстрока слова).
- Стоимость: сложность `ключи × строки` на файл; при 596 ключах и ТЗ на
  2–5 тыс. строк это ~1–3 млн fuzzy-вызовов на файл, ×10–70 файлов на задачу.
  Релевантных для закупки терминов — десятки, т.е. переплата ~10–50×.

## 2. Как должно быть

### 2.1. Прямая поставка (DIRECT_GOODS / DIRECT_SUPPLY)

Категория известна заранее (её присвоила модель/правила) — значит keyword-поиск
чужой таксономией вообще не нужен. Задача другая: **разобрать саму поставку**.

Извлекаем по документу:

- **полная смета / спецификация** — из чего состоит закупка (позиции, кол-во,
  ед. изм., цена за ед., сумма);
- **технические параметры** закупаемого (характеристики, бренд/модель, ГОСТ/ТУ);
- **требования к поставщику** (лицензии, опыт, соответствие);
- **требования к поставке** (сроки, адрес/базис, условия приёмки, гарантия);
- **условия участия** (обеспечение, порядок, ограничения).

Поиск терминов — только внутри **своей** категории (подтверждение/уточнение
подкатегории), без чужих категорий и без generic-стемов.

### 2.2. Объект / в составе работ (EMBEDDED_MATERIAL, PROJECT)

Пока без изменения логики, **кроме одного**: не искать всё подряд.

- Категории для закупки уже определены (модель потратила ресурс заранее —
  «путь от обратного»), поэтому в документах ищем **только термины этих
  категорий**.
- Термины без `category_codes` — только строгий `EXACT`, роль `CONTEXT`,
  находок не создают.

### 2.3. Роли терминов (общее для обоих)

`ENTITY` (сам товар/материал) · `QUALIFIER` (уточнение, напр. «класс 34/43») ·
`CONTEXT` (объект/работы) · `NOISE` (общие слова, стемы-обрубки).
Находку формирует только `ENTITY`; всё остальное — атрибут или отбрасывается.
Кросс-категорийный guard: термина чужой категории не может подтвердить закупку.

## 3. Этапы

1. **Scope по категории** (самый дешёвый и самый большой эффект): матчер
   получает только ключи категорий закупки (`keyword_meta[k].category_codes` ∩
   категории opportunities). 596 → десятки ключей.
2. **Роли и guard**: `ENTITY/QUALIFIER/CONTEXT/NOISE`, кросс-категорийное
   вето, ограничение усечения стемов.
3. **DIRECT-экстрактор**: смета/спецификация + техпараметры + требования
   (поставщик/поставка/участие) — отдельный контур, не keyword-поиск.
4. **UI**: для DIRECT — вкладки «Смета», «Техпараметры», «Требования»;
   для PROJECT — «Категорийные находки» (как сейчас), всё в карточке закупки.

## 4. Ограничения

- Scoring, пороги медалей, lifecycle и историю не меняем.
- Старые находки не удаляем; новые правила применяются к новым прогонам,
  старые остаются `LEGACY_UNVERIFIED` и отсекаются фильтром.
- XML-парсеры S7 не трогаем.
