# Шаблоны нормализации документов закупок

Статус: **черновик v0, для согласования**. Относится к карточке закупки и
контуру извлечения (DIRECT + EMBEDDED). Скоринг, медали и данные не меняет.

## 1. Что такое «шаблон нормализации»

Шаблон — это описанное в коде правило: **как выглядит таблица конкретного
документного семейства** (смета, ООЗ, ТЗ, проект договора) и **как из неё
собрать позиции с их характеристиками**. Шаблон отвечает на три вопроса:

1. **Распознавание** — это таблица нужного семейства? (подписи шапки, число
   колонок, структура строк);
2. **Извлечение** — где в строке позиция товара, где характеристика, где
   значение, где единица измерения;
3. **Валидация** — можно ли этому доверять (сверка позиции со сметой,
   обязательность количества/единицы, цитата-источник).

Шаблон — не «пример конкретной закупки», а форма: он обязан работать на всех
закупках с такой же формой и не срабатывать на чужих.

## 2. Слои нормализации

| Слой | Что делает | Где живёт | Статус |
|---|---|---|---|
| L0 | сырьё: таблицы и строки, разобранные из файла | кэш `/var/cache/crm_direct_parse`, воркерный парсер | есть |
| L1 | распознавание шаблона и извлечение (позиция/характеристика/значение/ед.) | `direct_document_extractor.py` | частично |
| L2 | нормализация полей: единицы (семейства измерения), названия | `UNIT_NORMALIZER_V1`, `direct_estimate_table.py` | частично |
| L3 | привязка «характеристика → позиция товара» | `direct_requirement_classifier.py` (`item`) | **в работе** |
| L4 | модельный добор: формы, которых нет в шаблонах | `structured_fact_extractor` (qwen2.5:7b) | контур есть, к карточке не подключён |
| L5 | доверие и показ: что показываем как факт | `structured_fact_trust_state`, карточка | частично |

Правило: **сначала детерминированный шаблон, модель — только там, где шаблона
нет.** Модель дороже, медленнее и не даёт гарантий воспроизводимости, поэтому
она закрывает остаток, а не основную массу.

### T8 подробнее

Смету и техпараметры дают не все документы закупки. Конкурсная документация
по оценке заявок содержит таблицы критериев и показателей, описание объекта
закупки — КТРУ/КОЗ, проект договора — график оплаты. Структурно они похожи на
смету (есть «наименование», «цена», «сумма»), поэтому попадали в «Смету».

Правило: `_is_estimate_source(name)` в `direct_document_extractor.py` —
перечисленные роли документов не порождают `spec`/`spec_tech`/`tech`.
Текстовые разделы (требования к участнику, обеспечение, товар) из этих файлов
извлекаются как раньше.

Проверка: 459603 (№ 0848300069526000365) — до правила в «Смете» были критерии
оценки, платёжный график и перечень КТРУ/ОКПД; после — 3 строки только из
«Расчёта НМЦК», а оценка даёт **1 позицию** «Выполнение работ по текущему ремонту…»
на 539 339,28 ₽ (`nmck_diff = 0`). Выборка 57 закупок: ни одна не потеряла
смету целиком, выпало 19 строк — все из «Проект контракта» и приложений.

### T8-категория: подготовка основания под полы (2026-10-11)

Наблюдение по 459603: «мастика» (подготовка/подложка под покрытие) лежала
только в шаблоне `waterproofing`, поэтому при скоупе по `flooring` не искалась
вовсе. В подкатегорию `flooring/screed_base` («Стяжка и подготовка основания»)
добавлены термины: `мастика`, `мастика для пола`, `клеящая мастика`
(в категории стало 266 активных термов).

Эффект проверен на 459603: скоуп `flooring` вырос с 205 до 208 ключей, и мастика
впервые попала в находки (+19). Но **метка категории осталась `waterproofing`**:
та же фраза есть и в гидроизоляции, а атрибуция категории у матчера выбирает
свою категорию термина, а не скоуп закупки. То есть шаблон даёт **recall**
(находим), но не **label** (как называем). Если нужен ярлык `flooring`, нужно
либо убрать дубль из `waterproofing`, либо делать атрибуцию scope-aware.

T6 и T7 — ответ на исходный вопрос «где ноутбук, где ПК, где монитор»: без
привязки к позиции одинаковые строки («Оперативная память 16 ГБ») неразличимы.

## 4. Порядок добавления шаблона

1. **Замер.** `scripts/probe_document_shapes.py` по корпусу → список форм с
   частотой и примерами. Новые формы берём по частоте, а не по одной закупке.
2. **Правило.** Описать распознавание (подписи шапки) и колонки; правило
   обязано возвращать `None`, если форма не совпала.
3. **Валидация.** Проверка на N закупках этой формы: потерь нет
   (`вход = выход`), каждая запись хранит файл и цитату, позиция подтверждена
   сметой или колонкой товара.
4. **Приёмка.** Прогон на контрольных закупках (как DIRECT-SUPPLY-CARD-TABS-1
   на 459631) + новых 10–15 закупках той же формы; результат в
   `docs/REFACTORING_PLAN.md`.
5. **Раскатка.** Только после приёмки; откат — выключением шаблона (флаг), без
   потери сырых данных.

## 5. Критерии приёмки (для любого шаблона)

- **Никаких потерь.** Все извлечённые записи остаются видимыми: либо в
  нормализованном блоке, либо в «не нормализовано»; вход = выход.
- **Провенанс.** У каждой нормализованной записи есть файл и цитата.
- **Точность привязки.** «Требование → позиция» ставится только при
  подтверждении (колонка товара либо строка-заголовок, сверенная со сметой);
  сомнительное не привязываем, а помечаем.
- **Единицы.** Значения с единицами приводятся к семейству измерения
  (`COUNT/AREA/LENGTH/MASS/VOLUME`); несовместимые единицы не «приводятся»
  насильно.
- **Воспроизводимость.** Шаблон детерминирован: тот же вход → тот же выход.

## 6. Где здесь модель (L4)

Модель (`structured_fact_extractor`, qwen2.5:7b, `structured_entities` +
`structured_attributes`) применяется, когда:

- форма документа не совпала ни с одним шаблоном;
- характеристики лежат в тексте, а не в таблице;
- нужно предложить нормализованное имя/бренд/модель там, где требуется
  коммерческая идентификация.

Модель обязана возвращать цитату на каждый факт и писаться с trust-state,
иначе такой факт не показывается как подтверждённый. Карточка показывает
нормализованное только из подтверждённых записей.

## 7. Что смотреть в карточке

- блок «Позиции товара» — требования, привязанные к позиции (когда документ
  даёт колонку товара или сработал шаблон T6);
- блок «Без привязки к позиции» — сгруппировано по смыслу (текущее поведение);
- «Итого/Всего/сумма» не показываются как характеристика товара;
- одинаковые характеристики показываются одной строкой с числом повторов.
