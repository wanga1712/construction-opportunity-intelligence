# Мультипрофильный демон обработки документации

Дата фиксации: 2026-07-23

## Ключевое решение

Один физический демон — но профильная очередь.

То есть мы не запускаем отдельный полный демон под каждого пользователя: это бы качало одни и те же архивы несколько раз. Но мы также не прогоняем каждый объект по всем направлениям.

Правильная схема:

1. дешёвый роутинг решает, каким профилям объект потенциально подходит;
2. если объект не подходит ни одному профилю — документы не скачиваются;
3. если подходит хотя бы одному профилю — документы скачиваются и парсятся один раз;
4. извлечённый текст прогоняется только по профилям-кандидатам;
5. результаты сохраняются отдельно по связке:

```text
tender / document / file
  -> search_profile
  -> product_group
  -> decision / score / matched_terms / ai_payload
```

## Почему так

Пример с улицей:

- для напольных покрытий “улица / дорога / мост” почти всегда мусор;
- для светотехники улица — сильный сигнал;
- для Стандартпарка улица может означать бордюр, водоотвод, лотки;
- для композитов мост/путепровод может означать перила, ограждения, композитные лотки.

Значит объект не должен удаляться глобально. Он должен получить разные решения по разным профилям.

## Сколько воркеров

На текущем этапе:

- 1 общий воркер скачивания и парсинга;
- 6 профильных направлений:
  - Материалы / напольные покрытия;
  - Гидроизоляция / строительные объекты;
  - Светотехника;
  - Композиты;
  - Стандартпарк;
  - Компьютеры / ИТ.

Итого: 7 логических веток, если считать общий downloader/parser.

Физически стартуем с одного демона на компьютере `sergey`, внутри которого профильная обработка выполняется после роутинга.

## Профили

Файл конфигурации: `document_processor/search_profiles.json`.

Профили должны синхронизироваться с CRM-таблицами:

- `crm_search_profiles`;
- `crm_product_groups`;
- `crm_search_profile_groups`;
- `crm_object_profile_decisions`;
- `crm_ai_training_events`.

## Роутинг до скачивания

Перед постановкой документов в очередь система должна определить `candidate_profiles`.

Минимальные входные данные:

- название закупки/объекта;
- ОКПД2;
- регион;
- источник: 44-ФЗ / 223-ФЗ / 615-ПП / NashDom / экспертиза;
- сегмент объекта: жилой, социальный, коммерческий, промышленный, дороги/благоустройство, прочее;
- статус: новая / разыгранная / документы в очереди / документы разобраны;
- пользовательские стоп-слова и ключевые фразы.

AI получает подсказки профилей (`ai_routing_hint`) и возвращает список профилей-кандидатов.

## Правило стоп-слов

Стоп-слово пользователя не убивает закупку для всех.

Пример:

- для напольных покрытий “улица” может быть мусором;
- для светотехники “улица” — сильный сигнал;
- для бордюрного камня и водоотвода “благоустройство” — сильный сигнал.

Поэтому:

- глобальные стоп-слова применяются только к очевидному мусору;
- профильные стоп-слова применяются только внутри конкретного профиля;
- если хотя бы один профиль видит потенциал, объект остаётся в общей базе;
- документы скачиваются только для объединения профилей-кандидатов.

## Компьютеры / ИТ

Компьютерный профиль — отдельный контур.

Модель должна читать ТЗ и оценивать возможность участия по рынку:

- ноутбук/ПК/моноблок/сервер;
- бюджет и НМЦ;
- CPU/RAM/SSD;
- количество USB/HDMI/LAN;
- ОС и гарантия;
- запретные/спорные требования;
- рыночная исполнимость конфигурации.

Пример: “ноутбук до 50 тыс., слабые параметры, но 4 USB-порта” — это не просто keyword-match, а задача сопоставления ТЗ с реальными рыночными моделями.
