## 1. Executive Summary

Модуль 2 — это автономный документальный процессор, который превращает сырую тендерную массу в квалифицированные лиды.

Он берёт из базы данных тендеры, прошедшие первичную фильтрацию (ОКПД, регион, стоп-слова), скачивает прикреплённую документацию с zakupki.gov.ru, извлекает из неё текст (включая OCR для отсканированных PDF), ищет в тексте ключевые слова из продуктового каталога клиента, сохраняет результаты с точной локализацией совпадений и выгружает релевантные файлы на Яндекс.Диск.

На выходе — структурированные данные, готовые к передаче в CRM: какой тендер, какой документ, какое ключевое слово найдено, в какой строке/ячейке, с каким уровнем уверенности.

Модуль работает как постоянный системный демон под управлением systemd, без ручного вмешательства.

### Поток данных (end-to-end)

```
БД: reestr_contract_44/223_fz
    + links_documentation_44/223_fz
         │
         ▼
[QueueManager.populate_queue()]
  Фильтр: ОКПД + регион + стоп-слова
  INSERT → document_processing_queue (status=pending)
         │
         ▼
[QueueManager.get_next_batch()]
  UPDATE status=processing FOR UPDATE SKIP LOCKED
  → список задач (contract_reg_number, table_source)
         │
         ▼ (параллельно: скачивание N+1 пока парсится N)
[Downloader.get_links()]
  SELECT из links_documentation_*
  → filter_links() — убираем .xml, .sig, без расширения
         │
         ▼
[Downloader.download_and_extract()]
  4 стратегии: прямой → прокси → HTML → финальный прямой
  Параллельно до DOWNLOAD_PARALLEL потоков
  → validate_open() — проверка целостности
  → ArchiveExtractor.extract_recursive() — ZIP/RAR рекурсивно
         │
         ▼
[TaskPipeline.process_task_with_files()]
  Для каждого файла:
    ParserFactory → нужный парсер
    PDF + OCR=1 → parse_pdf_incremental() (постранично, с курсором)
    Excel → parse_with_meta() → (text, line_meta с координатами ячеек)
    Остальные → parse() → text
         │
         ▼
[KeywordMatcher.process_text()]
  Нормализация OCR-артефактов
  Склейка соседних строк
  Fuzzy matching (rapidfuzz)
  Strict matching для коротких/артикульных слов
  Числовая точность, word coverage, stem fallback
  Дедупликация: лучшее совпадение на строку
  Stop-phrase фильтр
         │
         ▼
[FileEnhancer]
  highlight_matches() — жёлтая подсветка в DOCX/XLSX
  rename_file() — префикс с номером контракта
         │
         ▼
[YandexDiskClient.upload_matched_file()]
  OAuth REST API → WebDAV fallback
  Путь: {base}/{registry_type}/{contract_number}/
         │
         ▼
[MatchRepository.save_matches()]
  INSERT/UPDATE tender_document_matches
  INSERT tender_document_match_details (с деталями по каждому совпадению)
  ProcessedRegistry.finalize_file_status() → processed_documents
         │
         ▼
[QueueManager.mark_completed()]
  UPDATE document_processing_queue status=completed
  cleanup() → rm -rf temp dir
```

## 3. Логика отбора и запуска обработки

| Этап | Что происходит | Откуда данные | Результат | Комментарий |
|---|---|---|---|---|
| Первичный фильтр | JOIN по ОКПД, регион, исключение стоп-слов в названии | `user_search_settings`, `okpd_from_users`, `stop_words_names`, `collection_codes_okpd` | Список тендеров для обработки | Подтверждено кодом. Батчевый обход по диапазонам ID чтобы не падать по таймауту |
| Постановка в очередь | INSERT в `document_processing_queue` с `status=pending` | Реестры `reestr_contract_44/223_fz` и `_awarded` | Задача в очереди | Уникальность по `(contract_reg_number, table_source)` — дублей нет |
| Захват батча | `UPDATE ... FOR UPDATE SKIP LOCKED` | `document_processing_queue` | Атомарный захват N задач воркером | Гарантирует что два воркера не возьмут одну задачу |
| Приоритет реестров | 44-ФЗ → 44-ФЗ awarded → 223-ФЗ → 223-ФЗ awarded | Поле `table_source` | Порядок обработки | Подтверждено кодом (CASE в ORDER BY) |
| Защита от повтора файла | Проверка `processed_documents` перед скачиванием | `processed_documents` | Пропуск уже обработанных | `REPROCESS_COMPLETED=1` позволяет принудительно перезапустить |
| Сброс зависших | При старте: `processing → pending` для своего worker_id или старше N минут | `document_processing_queue`, `processed_documents` | Откат зависших задач | `STALE_TASK_MINUTES` (по умолчанию 60) |
| Контроль памяти | Проверка RSS процесса перед каждой задачей | `psutil` | Прерывание батча при превышении лимита | `MEMORY_LIMIT_BYTES` (по умолчанию 4GB) |
| Контроль очереди | Пополнение только если `pending < 50` | `document_processing_queue` | Не перегружает очередь | `QUEUE_POPULATE_LIMIT` — сколько добавлять за раз |
| Обработка ошибок | `status=error` + сообщение в `error_message` | — | Задача помечена как ошибочная | `REQUEUE_ERRORS=1` переводит error → pending для повтора |

## 4. Обработка документов

| Тип файла | Как обрабатывается | Извлекаемые данные | Ограничения | Комментарий |
|---|---|---|---|---|
| `.pdf` (текстовый) | PyPDF2 `extract_text()` постранично | Текст по страницам | Не работает с зашифрованными PDF | Детектирует "мусорный" текст (mojibake) и переключается на OCR |
| `.pdf` (отсканированный) | pdf2image → pytesseract OCR | Текст через OCR | Медленно (~16 мин/файл с OCR), требует tesseract | Постраничный с курсором возобновления. `ENABLE_OCR=1`, `ENABLE_OCR_PAGED=1` |
| `.docx` | python-docx | Текст параграфов + подсветка совпадений | Не извлекает таблицы отдельно | Поддерживает highlight жёлтым цветом |
| `.doc` | antiword → libreoffice → raw binary | Текст | Требует antiword на сервере | Три fallback стратегии |
| `.xlsx` / `.xlsm` | openpyxl `parse_with_meta()` | Текст + координаты ячеек (лист, строка, колонка, адрес) | Большие файлы медленно | Единственный формат с точной локализацией до ячейки |
| `.odt` | zipfile + xml.etree (OpenDocument) | Текст | Базовое извлечение | Подтверждено кодом |
| `.gsfx` | zipfile + xml.etree (SmetaWIZARD) | Текст из смет | Специфичный формат | Редкий, но важный для строительных тендеров |
| `.txt`, `.csv`, `.log`, `.xml`, `.html` | встроенный `open()` | Текст как есть | — | TextParser как fallback |
| `.zip` | zipfile, рекурсивно | Все вложенные файлы | Глубина вложенности до 3 уровней | Кириллица в именах через cp437→utf-8 |
| `.rar` | unrar subprocess | Все вложенные файлы | Требует unrar на сервере | Поддержка многотомных архивов (.r00, .r01...) |
| `.xml`, `.sig`, `.p7s` | Пропускаются до скачивания | — | — | Контракты ЕИС и подписи — бесполезны для анализа |
| Без расширения | Пропускаются до скачивания | — | — | "Информация о контракте" и подобные |

**Pre-download фильтрация** (подтверждено кодом): до скачивания отсеиваются файлы по точному имени, префиксу и расширению. Расширяется через `skip_files.json` без изменения кода.

**Стратегии скачивания** (4 уровня fallback):
1. Прямой запрос с имитацией браузера (User-Agent, Referer)
2. Через прокси (только для файлов < 10MB)
3. HTML-парсинг страницы и извлечение filestore-ссылок
4. Финальная прямая попытка

**Валидация после скачивания**: PDF → PyPDF2, DOCX → python-docx, XLSX → openpyxl. При неудаче — повторное скачивание (до 2 попыток).

## 5. Логика поиска совпадений

| Источник / правило | Что ищется | Как ищется | Как фильтруется | Результат |
|---|---|---|---|---|
| `product_catalog_2.products.name` | Названия продуктов из каталога клиента | Fuzzy matching (rapidfuzz) | Стоп-слова, числовая точность, word coverage | Основной словарь ~889 слов |
| `user_keywords.json` / `DOCUMENT_EXTRA_PHRASES_JSON` | Дополнительные фразы пользователя | То же | То же | Расширение без перезапуска |
| `EXTRA_KEYWORDS` (env) | Фразы через запятую | То же | То же | Быстрое добавление |
| `keyword_thresholds.json` | Индивидуальные пороги для конкретных фраз | — | Переопределяет `MATCH_MIN_SCORE` | Тонкая настройка точности |
| `document_stop_phrases` (БД) | Стоп-фразы — блокируют ложные совпадения | Если keyword входит в стоп-фразу И стоп-фраза есть в тексте | Совпадение отбрасывается | Фильтр ложных срабатываний |

**Алгоритм matching** (подтверждено кодом):

| Тип keyword | Метод | Порог |
|---|---|---|
| ≤5 символов или артикул "БМ XXXX" | Regex с границами слов (строгий) | Точное вхождение |
| Длинные фразы, строка ≈ длине keyword | `fuzz.ratio` | `MATCH_MIN_SCORE` (по умолчанию 75) |
| Длинные фразы, строка >> keyword | `fuzz.token_set_ratio` | То же |
| Score 50–75, многословный keyword | Stem coverage fallback (корни слов) | ≥80% корней найдено |

**Дополнительные проверки**:
- Word coverage: ≥70% значимых слов keyword должны быть в строке
- Числовая точность: все числа из keyword должны быть в строке (word boundary)
- OCR нормализация: латинские омоглифы → кириллица, дефисы → пробелы, стык буква↔цифра
- Склейка соседних строк: ищет фразы разбитые переносом строки
- Дедупликация по строке: на одной строке — только лучшее совпадение (score MAX)

**Уровни уверенности**:
- `green`: score ≥ 95 (высокая уверенность)
- `yellow`: score 75–94 (средняя уверенность)

**Локализация совпадения**:
- PDF/TXT: номер строки
- XLSX: лист + номер строки + буква колонки + адрес ячейки (напр. `B12`)
- DOCX: номер строки параграфа

## 8. Масштабируемость

### Что уже масштабируется (подтверждено кодом)

- **Горизонтальное масштабирование воркеров**: `WORKER_ID` + `FOR UPDATE SKIP LOCKED` — можно запустить N экземпляров демона параллельно без конфликтов
- **Параллельное скачивание**: `DOWNLOAD_PARALLEL` потоков внутри одной задачи
- **Pipeline download+parse**: скачивание задачи N+1 идёт параллельно с парсингом задачи N
- **Батчевый обход реестров**: обход по диапазонам ID, не падает на таблицах с 30k+ строк
- **OCR с курсором**: прерванный OCR продолжается с последней страницы, не с начала
- **Расширяемые словари**: добавление новых ключевых слов через JSON-файл или env без перезапуска кода
- **Расширяемые фильтры файлов**: `skip_files.json` без изменения кода
- **Поддержка нескольких реестров**: 44-ФЗ, 223-ФЗ, awarded — единая логика

### Что масштабируется ограниченно

- **Память**: один воркер держит все ~889 ключевых слов в RAM. При росте каталога до 10k+ слов — время матчинга вырастет линейно (O(keywords × lines))
- **Локальный диск**: временные файлы хранятся локально. При параллельных воркерах на одном сервере — конкуренция за диск
- **Яндекс.Диск**: один токен, нет rate-limit handling кроме retry. При высокой нагрузке — возможны ошибки загрузки
- **OCR**: pytesseract однопоточный, CPU-bound. Один воркер = одна страница OCR за раз

### Что нужно доработать для промышленного масштаба

- Вынести OCR в отдельный микросервис с очередью (Celery/RQ)
- Вынести keyword matching в отдельный stateless сервис
- Заменить локальный диск на S3-совместимое хранилище
- Добавить rate-limit и retry с backoff для Яндекс.Диска
- Добавить метрики (Prometheus/Grafana) — сейчас только логи
- Multi-tenant: сейчас один каталог продуктов на всех, нужна изоляция по клиенту

## 9. Риски и ограничения

Только реальные выводы из кода:

| Риск | Описание | Серьёзность |
|---|---|---|
| **Точность fuzzy matching** | Порог 75 даёт ложные срабатывания на коротких или похожих словах. Дедупликация по строке снижает шум, но не устраняет | Средняя |
| **Нет поддержки .pptx, .rtf, .msg** | Презентации и письма не обрабатываются | Низкая (редко в тендерах) |
| **OCR только русский+английский** | `lang="rus+eng"` в pytesseract. Другие языки не поддерживаются | Низкая |
| **Производительность OCR** | ~16 минут на файл с OCR. При большом объёме отсканированных PDF — узкое место | Высокая |
| **Локальный диск** | Временные файлы на диске воркера. Диск заполнился → БД упала (наблюдалось в production) | Высокая |
| **Нет автоочистки downloads** | Cleanup вызывается в `finally`, но при краше процесса папки остаются | Средняя |
| **Дедупликация совпадений** | Реализована на уровне строки (лучший score). Одинаковые фразы в разных файлах одного тендера — сохраняются все | Низкая |
| **Отказоустойчивость Яндекс.Диска** | При недоступности — файл сохраняется в `failed_uploads/`, но не перезагружается автоматически | Средняя |
| **Нет тестового покрытия pipeline** | Тесты есть для matcher и text extraction, но нет интеграционных тестов полного цикла | Средняя |
| **Зависимость от внешних бинарей** | `unrar`, `antiword`, `tesseract`, `pdftoppm` — должны быть установлены на сервере | Средняя |
| **Один поток OCR** | pytesseract не параллелится внутри одного воркера | Средняя |
| **Память при большом PDF** | OCR конвертирует страницу в изображение в RAM. Большие PDF → MemoryError (наблюдалось в production) | Высокая |

## 10. Продуктовая ценность

*(Язык для презентации)*

**Проблема, которую решает модуль:**
Менеджер по продажам тратит часы на ручной просмотр тендерной документации — технических заданий, смет, спецификаций — чтобы понять, нужна ли там его продукция. Большинство тендеров оказываются нерелевантными. Но пропустить нужный — значит потерять контракт.

**Что делает модуль:**
Система автоматически скачивает документацию по каждому тендеру, прошедшему первичный фильтр, и проверяет её на наличие ваших продуктов. Не просто по названию тендера — а внутри каждого документа: в технических заданиях, сметах, спецификациях, приложениях.

**Ключевые преимущества:**

- *Скорость*: система обрабатывает документы 24/7 без участия человека. Менеджер видит результат уже готовым.
- *Точность локализации*: система не просто говорит "нашли совпадение" — она показывает конкретную строку, ячейку таблицы, страницу документа.
- *Работа с любыми форматами*: PDF (включая отсканированные), Word, Excel, сметы SmetaWIZARD, архивы ZIP/RAR.
- *Адаптация под продуктовую линейку*: словарь ключевых слов берётся из вашего каталога продукции. Добавили новый продукт — система сразу начинает его искать.
- *Подсвеченные документы*: релевантные файлы автоматически загружаются на Яндекс.Диск с жёлтой подсветкой найденных слов — менеджер сразу видит что именно совпало.
- *Проектные сигналы раньше конкурентов*: система мониторит тендеры в момент их появления, не дожидаясь пока их заметит конкурент.

## 11. Тезисы для презентации

*(Готовые слайды)*

**Слайд: Что это**
> Модуль автоматического анализа тендерной документации — второй уровень системы TenderMonitor. Превращает тендерную массу в квалифицированные лиды для отдела продаж.

**Слайд: Как работает**
> 1. Берёт тендеры, прошедшие фильтр по ОКПД и региону
> 2. Скачивает всю прикреплённую документацию (PDF, Word, Excel, архивы)
> 3. Извлекает текст — включая OCR для отсканированных документов
> 4. Ищет ваши продукты внутри каждого документа
> 5. Сохраняет результат: что найдено, где, с какой уверенностью
> 6. Загружает подсвеченные файлы на Яндекс.Диск

**Слайд: Форматы документов**
> PDF (текст + OCR) · Word (.docx, .doc) · Excel (.xlsx, .xlsm) · OpenDocument (.odt) · Сметы SmetaWIZARD (.gsfx) · Архивы ZIP/RAR (включая вложенные)

**Слайд: Точность поиска**
> Нечёткий поиск (fuzzy matching) с настраиваемым порогом уверенности. Два уровня: зелёный (≥95%) и жёлтый (75–94%). Числовая точность: "Стармекс РМ 331" не совпадёт с "Стармекс РМ 334". Фильтр стоп-фраз исключает ложные срабатывания.

**Слайд: Масштабируемость**
> Несколько воркеров работают параллельно без конфликтов. Атомарный захват задач через PostgreSQL SKIP LOCKED. Горизонтальное масштабирование без изменения кода.

**Слайд: Интеграция с CRM**
> Результат — структурированные данные: тендер + документ + найденное слово + позиция в документе + ссылка на Яндекс.Диск. Готово к передаче в любую CRM через API или прямое подключение к БД.

**Слайд: Адаптация под клиента**
> Словарь ключевых слов = ваш каталог продукции. Добавили новый продукт — система сразу начинает его искать во всех новых тендерах. Дополнительные фразы и индивидуальные пороги — без изменения кода.

## 12. Зрелость продукта

### Что уже выглядит как продукт
- Полный автономный pipeline от БД до Яндекс.Диска
- Поддержка 8+ форматов документов включая OCR
- Многоуровневый fuzzy matching с числовой точностью и дедупликацией
- Горизонтальное масштабирование через worker model
- Структурированное хранение результатов с локализацией до ячейки
- Systemd-демон с автозапуском, контролем памяти и CPU
- Retry-логика, stale task recovery, failed_uploads fallback

### Что пока выглядит как внутренняя разработка
- Нет API для внешних систем — только прямой доступ к БД
- Нет UI для мониторинга — только логи и journalctl
- Нет автоматической перезагрузки файлов из `failed_uploads/`
- Нет метрик (Prometheus/Grafana)
- Нет интеграционных тестов полного цикла
- Конфигурация через env-переменные без валидации схемы
- Яндекс.Диск как единственное облачное хранилище (нет S3/GCS)

### Что нужно для коммерческой зрелости
- REST API для интеграции с CRM (webhook или polling)
- Multi-tenant изоляция: отдельный каталог продуктов и настройки на клиента
- Dashboard мониторинга: очередь, скорость обработки, ошибки
- Автоматическая повторная загрузка из `failed_uploads/`
- Поддержка S3-совместимого хранилища вместо/вместе с Яндекс.Диском
- SLA-метрики: время от появления тендера до результата в CRM
- Документация API и onboarding для новых клиентов
