# Базовые правила мультипрофильного поиска

Дата фиксации: 2026-07-23

## Главный принцип

Объект, закупка или документ существуют в системе один раз.

Решение о релевантности принимается отдельно для каждой связки:

```text
source_object + user_profile + product_group
```

То есть один и тот же объект может быть:

- нерелевантен для напольных покрытий;
- релевантен для светотехники;
- релевантен для бордюрного камня;
- нерелевантен для компьютеров;
- интересен для гидроизоляции только при наличии подземной части.

## Что нельзя делать

Нельзя удалять объект глобально из CRM только потому, что он не подходит одному пользователю или одной товарной группе.

Пользовательское стоп-слово не должно убивать объект для всех.

## Уровни правил

### 1. Глобальные правила

Глобальные правила применяются ко всем пользователям и товарным группам.

Примеры глобального мусора:

- покупка квартиры;
- аренда помещения;
- услуги охраны;
- страхование;
- питание;
- обучение сотрудников;
- банковские услуги;
- юридические услуги;
- заведомо не объектная закупка.

Результат:

```text
global_reject
```

Такой объект можно скрывать из активных очередей всех пользователей.

### 2. Правила пользователя

Правила пользователя применяются только к конкретному профилю.

Пример:

- пользователь по напольным покрытиям режет «бордюрный камень»;
- пользователь по благоустройству наоборот считает «бордюрный камень» сильным сигналом;
- пользователь по компьютерам режет строительные работы;
- пользователь по светотехнике оставляет улицы, дороги, благоустройство.

Результат:

```text
profile_reject / profile_keep / profile_review
```

### 3. Правила товарной группы

Товарная группа имеет свои признаки интереса.

Примеры:

- **Напольные покрытия:** линолеум, ПВХ-плитка, ковролин, спортивное покрытие, наливной пол.
- **Светотехника:** светильники, опоры освещения, уличное освещение, LED, освещение территории.
- **Бордюрный камень:** бордюр, бортовой камень, благоустройство, дороги, тротуары.
- **Водоотвод:** лотки, дождеприёмники, дренаж, водоотведение.
- **Гидроизоляция:** подвалы, паркинги, подземные этажи, протечки, гидроизоляционные работы.
- **Компьютеры:** ноутбуки, ПК, моноблоки, серверы, рабочие станции, периферия, ТЗ с характеристиками.

## Документация

Документы нужно скачивать и парсить один раз.

После извлечения текста документ прогоняется по всем активным профилям и товарным группам:

```text
document_text
  -> product_group: floors
  -> product_group: lighting
  -> product_group: curbstone
  -> product_group: computers
  -> ...
```

Результаты сохраняются отдельно:

```text
object_id + user_profile_id + product_group_id + decision
```

## Конфликт правил

Если один профиль режет объект, а другой оставляет:

- объект остаётся в общей базе;
- в выдаче первого профиля объект скрывается;
- в выдаче второго профиля объект показывается;
- AI получает конфликт как обучающий сигнал.

Пример:

```text
Закупка: благоустройство улицы

Профиль "Напольные покрытия":
  decision = reject
  reason = улица / благоустройство / нет полов

Профиль "Светотехника":
  decision = keep
  reason = возможно наружное освещение

Профиль "Бордюрный камень":
  decision = keep
  reason = благоустройство / тротуары / дороги
```

## Статусы решения

Рекомендуемые значения:

- `global_reject` — мусор для всех;
- `profile_reject` — мусор для конкретного профиля;
- `profile_keep` — релевантно конкретному профилю;
- `profile_review` — нужна ручная проверка;
- `needs_documents` — по названию недостаточно данных;
- `documents_queued` — документы поставлены в очередь;
- `documents_parsed` — документы разобраны;
- `qualified_lead` — подтверждённая возможность;
- `in_work` — менеджер взял в работу;
- `archived` — завершено/просрочено/убрано из активной очереди.

## AI-обучение

Каждое действие пользователя сохраняется как обучающее событие:

- подтвердил релевантность;
- отклонил;
- изменил товарную группу;
- изменил категорию объекта;
- добавил стоп-слово;
- добавил ключевое слово;
- указал причину отказа;
- взял в работу;
- перевёл в сделку.

AI должен использовать эти события для:

- переоценки похожих объектов;
- поиска похожих закупок;
- корректировки стоп-слов;
- уточнения приоритета;
- формирования следующего шага менеджеру.

## Правило сроков

Просроченные объекты нельзя показывать в активной очереди.

Для разыгранных закупок минимальный горизонт поставки:

```text
delivery_end_date >= current_date + 90 days
```

Если до окончания поставки меньше 90 дней, объект считается поздним и уходит в архив/низкий приоритет, если пользователь явно не вернул его в работу.

## Правило очереди по умолчанию

1. Новые неразыгранные закупки, где уже найдены совпадения в документах.
2. Разыгранные закупки с совпадениями и сроком поставки не меньше 90 дней от текущей даты.
3. Новые закупки, где документы ещё в очереди.
4. Разыгранные закупки, где документы ещё не разобраны, но срок ещё актуален.
5. Ранние объекты из радара без закупки — отдельный контур, не смешивать с закупочной очередью.
